전장에 들어갈 때 무기 목록에서 A의 설명서를 찾아 실제 전투 상태를 준비하는 거야.

그래서 장비 화면의 슬롯 오브젝트가 전투 씬까지 따라갈 필요는 없어.

저장된 장착 구성은 이어받고, 전투용 상태는 새로 만드는 구조야.

```mermaid

    A --> C["BossEncounterManager<br/>보스전이면 보스 생성"]
    A --> D["StageTransitionManager<br/>입장·구간 이동 연출"]
```

예를 들어 MidBossBattle로 바뀌면 보스 생성 담당이 자기 역할을 수행해.
구간 이동 연출이 끝나면 StageTransitionManager는 Flow에 완료를 알려. 그러면 Flow가 다음 상태로 바꾸고 다시 방송해.
Flow: “구간 전환을 시작한다.”
→ Transition: 실제 이동 연출
→ Transition: “전환이 끝났다.”
→ Flow: Section2로 변경
이 구조에서는 진행 상태의 결정과 화면에서 일어나는 연출이 연결되면서도 역할은 구분돼 있어.
12-6. 공격은 ‘발사 결정 → 공격체 행동 → 피해 적용’으로 이어진다
플레이어의 공격을 전체 흐름에 놓으면:

→ 현재 무기와 사용 가능 상태 확인
→ 공격 방식에 맞는 오브젝트 생성·초기화
→ Projectile 또는 개별 공격체가 이동·판정
→ 대상에게 피해 전달
일반적인 투사체 경로에서는 [Projectile.cs (line 120)](C:/YSJ/SubPF/Assets/2. Scripts/Weapon/Projectile/Projectile.cs:120)가 IDamageable을 통해 피해를 전달해.
여기서 IDamageable은 이렇게 이해하면 돼.
“너의 정확한 종류를 몰라도, 피해를 받을 수 있다면 이 약속대로 호출하겠다.”

그래서 일반 적과 보스가 서로 다른 부모 클래스를 사용하더라도, 공격체가 공통된 피해 처리 약속을 이용할 수 있어.
다만 레이저·폭발·근접 공격처럼 판정 방식이 다른 공격은 각각의 구현을 함께 읽어야 해. 모든 공격이 하나의 동일한 충돌 함수만 통과하는 구조는 아니야.
12-7. 적 하나를 처치하면 성장과 증강이 서로 다른 길로 흐른다
일반 적 처치를 예로 들면:
적이 피해를 받아 사망
 ├─ 보너스 게이지 반영
 ├─ 경험치 지급
 └─ 골드 드롭
여기서 두 가지 성장은 별개야.
경험치 경로
GameManager.AddExperience
→ 이번 판 획득 경험치 집계
→ CharacterProgression.AddExp
→ 레벨·경험치 갱신
→ 저장
→ 필요하면 업적 재평가
증강 경로
시간 경과 또는 적 처치 보너스
→ 증강 게이지 충전
→ 게이지가 차면 전투 정지
→ 증강 선택
→ 현재 플레이어 또는 무기에 적용
→ 전투 재개
따라서 레벨이 올랐다는 것과 증강 선택창이 열린다는 것은 같은 사건이 아니야.
현재 증강 선택은 GameManager의 게이지가 담당하고, 캐릭터 레벨은 CharacterProgression이 관리해.

보유 골드	저장 데이터를 읽어 이어감

이 차이를 알아야 “저장했는데 왜 강화가 없어졌지?” 같은 질문에도 정확히 답할 수 있어.

실패했다고 이미 저장된 경험치와 골드를 결과창에서 되돌리는 처리도 없어.
12-10. 일반 적 패턴과 보스 패턴은 같은 단어지만 운영 방식이 다르다
8~11단계를 나란히 놓으면 차이가 더 명확해져.

보스 패턴은 한 지휘관이 수행하는 작전 순서야.

또 보스 패턴 하나가 끝나도 이미 발사한 직진탄은 남을 수 있어. 패턴 실행 종료와 생성된 모든 공격체의 제거는 같은 조건이 아니야.
반면 Head의 블랙홀 패턴은 블랙홀 소멸까지 기다렸지. 이처럼 개별 패턴의 종료 기준도 함께 읽어야 해.
12-11. 네 프로젝트에서 반복해서 등장하는 설계 방식은 네 가지다
지금까지 배운 객체지향을 실제 코드와 연결하면 다음처럼 정리할 수 있어.

세 구현이 똑같지는 않지만, 공통된 목적은 있어.
여러 곳에서 참조하는 원본 설정과, 실행마다 달라지는 상태를 구분하는 것이야.
12-12. 장비와 증강의 MVP는 ‘화면과 규칙 사이의 연결 담당’을 둔 것이다
장비 화면에서는:
View
→ 사용자가 무엇을 눌렀는지 알림

Presenter
→ 요청을 받아 Model 호출

Model
→ 구매·장착 가능 여부와 데이터 처리

Presenter
→ 결과를 View에 반영
흐름을 사용해.
[EquipmentPresenter (line 133)](C:/YSJ/SubPF/Assets/2. Scripts/1.EquipmentManage/EquipmentPresenter.cs:133)는 구매가 성공하면 보유 골드와 슬롯 표시를 갱신해.
[UpgradePresenter (line 110)](C:/YSJ/SubPF/Assets/2. Scripts/Upgrader/UpgradePresenter.cs:110)는 선택한 증강이 플레이어 대상인지 무기 대상인지에 따라 다음 화면 흐름을 나눠.
플레이어 증강 선택
→ 적용 후 종료

무기 증강 선택
→ 대상 무기 선택 화면
→ 선택한 슬롯에 적용 후 종료
이 분리의 의미는 단순히 파일을 세 개로 늘린 데 있지 않아.
버튼의 모양과 연출이 바뀌는 일,
구매나 강화 규칙이 바뀌는 일,
선택 순서가 바뀌는 일을 구분해서 다루는 데 의미가 있어.

다만 프로젝트 전체의 모든 UI가 이 방식으로 통일된 것은 아니야. 예를 들어 현재 결과창은 표시뿐 아니라 클리어 기록 저장과 업적 평가 호출도 수행해.
실제 책임은 클래스 이름만 보고 판단하지 않고, 내부에서 무엇을 호출하는지 확인해야 해.
12-13. 마을 개편을 할 때도 이 구분이 그대로 도움이 된다

현재 [CharacterSelectScreen.LoadCharacter (line 429)](C:/YSJ/SubPF/Assets/2. Scripts/CharacterSelect/CharacterSelectScreen.cs:429)은 캐릭터를 확정하면서 선택 목적에 따라 다음 씬도 결정해.

- 전투 목적이면 선택한 StageN.
그래서 마을 개편에서는 선택 정보를 저장하는 역할과 화면 이동 방식이 어디서 연결되어 있는지가 중요한 확인 지점이 돼.
기존 CharacterData·WeaponData·저장 장착 정보·전투 초기화까지 모두 마을 화면의 모양에 종속된 것은 아니야.
마을은 앞으로 만들어질 입구이고, 지금 배운 데이터 전달과 전투 준비 구조는 그 입구에서 연결할 대상이라고 생각하면 돼. 구체적인 변경 설계는 기능 추가를 진행할 때 다루자.
12-14. 이제 프로젝트를 읽을 때 다섯 가지를 물으면 된다
앞으로 새로운 기능이 추가돼도 이 질문으로 흐름을 찾을 수 있어.
질문	확인할 내용
누가 시작시키는가?	버튼, 체력 이벤트, 시간 조건, 페이즈 변경
필요한 정보는 어디에서 오는가?	에셋, 저장 데이터, 세션, Initialize
현재 상태는 누가 보관하는가?	Model, RuntimeState, MonoBehaviour, 코루틴 지역 변수
실행이 끝났다는 기준은 무엇인가?	시간 종료, 오브젝트 소멸, 애니메이션 완료, UI 결과
결과를 누가 받아 무엇을 하는가?	저장, 다음 페이즈, UI 갱신, 다음 패턴 실행


예를 들어 Head의 혼란 패턴에 적용하면:
시작: 체력 조건으로 요청된 특수 패턴
정보: 패턴 에셋의 문자 수·시간·피해량
상태: UI의 입력 순서·남은 시간·생명
종료: 성공·실패·취소 결과
후속 처리: 패턴이 피해·연출·시간 복원
이렇게 하나의 기능을 처음부터 끝까지 설명할 수 있게 돼.
12-15. 취업용으로 네 프로젝트를 설명한다면
클래스 이름을 많이 나열하기보다, 플레이 흐름과 그 흐름을 가능하게 한 구조를 설명하는 편이 좋아.
예를 들면 이렇게 말할 수 있어.
“스테이지와 캐릭터 선택 정보를 세션에 보관하고, 전투 진입 시 저장된 장비 ID를 데이터베이스로 해석해 캐릭터와 무기 상태를 초기화합니다. 전투 진행은 페이즈 이벤트로 연결하고, 일반 적 소환과 보스 행동은 별도의 실행 구조로 관리합니다. 보스는 체력 조건과 시간 조건으로 패턴을 요청하며, 실행기가 우선순위에 따라 하나씩 수행합니다.”

설계 의도를 물으면:
“공유 설정과 실행 중 상태를 분리했습니다. 무기 에셋에는 기본 수치를 두고 전투 중 강화는 런타임 상태에 적용합니다. 보스 패턴도 실행 대상은 Context로 전달하고, 이번 실행의 진행 상태는 코루틴에서 관리합니다.”

구체적인 구현 사례를 물으면:
“Dog의 회전 난사는 균등한 각도의 직진탄 묶음을 발사하면서 시간에 따라 기준 발사각을 변경해 나선형 배열을 만듭니다. Head의 블랙홀은 플레이어 입력 속도에 외부 속도를 합산해 조작을 유지하면서 흡입을 표현합니다.”

이제 기존 12단계의 설명 흐름은 한 바퀴 마쳤어. 기능 추가를 이어갈 때는 새 기능이 이 지도에서 어디에 들어가는지 연결해서 보고, 추가가 끝나면 앞서 확인한 수정사항과 전체 설계를 함께 정리하자.
