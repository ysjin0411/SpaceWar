조금 더 구체적으로 보면 세 가지가 중요해.
첫째, SaveManager는 파일 담당자 이상의 일을 하고 있어.
파일 읽기·쓰기 외에도 구매, 장착, 슬롯 교환, 보유 기록 보정, 업적 보상, 최고 기록 갱신, 테스트 기능까지 맡아.
이건 클래스를 너무 많이 나눠서 생긴 과설계가 아니라, 한 클래스에 변경 이유가 많이 모인 상태에 가까워.
다만 지금 즉시 여러 인터페이스와 서비스로 분해하는 것부터 시작할 필요는 없어. 먼저 현재 규칙이 어디에 있는지 구분하는 게 우선이야.
둘째, 저장 객체를 외부에서 직접 바꿀 수 있어.
EquipmentModel은 기본 보유 무기를 저장 객체에 직접 추가하고, CharacterProgression은 레벨·경험치를 직접 바꿔.
동작 자체는 성립하지만, 수정과 파일 저장을 짝지어 기억해야 해.
담당자에게 변경을 요청하는 경로와, 기록부에 직접 쓰는 경로가 함께 존재한다.

이것이 현재 구조의 중요한 특징이야.
셋째, 구매·장착 규칙의 검증 위치가 다르다.
EquipmentModel.TryPurchase()는 레벨과 구매 가능 상태를 확인한 뒤 SaveManager에 구매를 요청해.
반면 SaveManager.TryPurchaseWeapon()은 전달받은 ID·가격을 사용하고, 요구 레벨을 직접 조회하지 않아.
장착도 Model은 보유 상태와 중복 장착을 확인하지만, SaveManager의 EquipWeapon()은 같은 검사를 수행하지 않아.
따라서 이렇게 이해하면 돼.
현재 장비 화면의 규칙은 EquipmentModel을 통과할 때 적용된다.
SaveManager를 직접 호출하는 다른 경로에는 같은 검사가 자동으로 따라붙지 않는다.

이것만으로 현재 UI에 구매 버그가 있다고 단정할 수는 없어. 다만 앞으로 다른 화면이나 보상 시스템에서 장비를 지급할 때, 어느 규칙을 거쳐야 하는지를 명확하게 해둘 필요가 있어.

2-5. 가장 중요한 C# 개념: 기록을 돌려받는 것은 복사본을 받는 게 아니다

이 부분을 이해하면 SaveManager, EquipmentModel, CharacterProgression이 연결되는 이유가 선명해져.

비유하면 기록부 한 장을 복사해 주는 게 아니라 다음처럼 말하는 거야.

따라서 다음 예시에서 loadout은 원래 기록과 연결되어 있어. 설명용 예시이며 프로젝트에 추가할 코드는 아니야.
// SaveManager가 보관하는 Soldier 기록 객체의 참조를 받는다.

// 이 한 줄만으로 JSON 파일까지 갱신되지는 않는다.
loadout.level = 5;

// 현재 메모리의 전체 저장 데이터를 JSON 파일에 기록한다.
SaveManager.Instance.SaveToFile();
그래서 실제 CharacterProgression도 자신이 참조하고 있는 저장 객체의 레벨·경험치를 수정한 뒤 SaveToFile()을 호출할 수 있어.
반면 파일은 객체의 변화와 자동으로 연결되어 있지 않아.
```mermaid
flowchart LR
    A["CharacterProgression<br/>레벨·경험치 계산"] -->|"필드 값 반영"| B["메모리의<br/>CharacterLoadoutSaveData"]
    B -->|"PlayerSaveData에 포함"| C["SaveToFile"]
    C -->|"JSON 변환 후 쓰기"| D["player_save.json"]
```



현재 SaveToFile()은 특정 캐릭터의 변경 부분만 저장하는 방식이 아니야. PlayerSaveData 전체를 JSON으로 변환해서 파일을 덮어써.
또 하나 짚고 넘어가자.
SaveManager에는 다음 프로퍼티가 있어.
// 내부 저장 객체의 참조를 외부에 반환한다.
// setter가 없어도 반환된 객체의 public 필드는 외부에서 변경할 수 있다.
public PlayerSaveData PlayerSaveData => _playerSaveData;
프로퍼티에 setter가 없다는 것과, 반환한 객체까지 읽기 전용이라는 것은 달라.
지금은 이 특성 덕분에 여러 곳에서 기록을 쉽게 수정할 수 있어. 동시에 “누가 값을 바꿨는지”, “수정 뒤 저장을 호출했는지”를 추적해야 하는 부담도 생겨. 이 부분은 마지막 설계 평가에서 다시 연결할게.

2-10. 그런데 경험치는 전투 중 얻는데 왜 다음 게임에도 남을까?

“전투 중 바뀌는 값은 전부 사라진다”라고 외우면 여기서 틀려.
어디에서 바뀌었느냐보다 저장 경로로 연결되어 있느냐가 중요해.
CharacterProgression.Initialize()는 저장된 레벨과 경험치를 읽어 자신의 현재 값으로 복사해.
전투 중 경험치를 받으면:
1. 현재 경험치를 증가시킨다.
2. 레벨업 조건을 충족하는 동안 레벨업을 처리한다.
3. 필요한 경험치와 남은 경험치를 다시 계산한다.
4. 저장 객체에 레벨과 경험치를 반영한다.
5. UI에 변경을 알린다.
6. SaveToFile()을 호출한다.
7. 레벨업했다면 업적을 검사한다.
현재 필요 경험치 공식은 다음과 같아.
다음 레벨에 필요한 경험치 = 100 + (현재 레벨 − 1) × 50

예를 들어 레벨 1, 경험치 90에서 경험치 30을 받으면:
- 현재 경험치가 120이 된다.
- 레벨 1의 필요 경험치 100을 소비한다.
- 레벨은 2가 된다.
- 경험치 20이 남는다.
- 레벨 2의 다음 필요 경험치는 150이다.
- 저장 기록에 레벨 2, 경험치 20을 반영하고 파일에 쓴다.
한 번에 많은 경험치를 받아 여러 번 레벨업할 수 있으므로 if가 아니라 while을 사용하고 있어.
그리고 현재 확인한 성장 경로에서는 레벨업이 기본 HP·무기 공격력을 자동으로 올리지는 않아.
레벨은 장비 요구 조건과 업적 판단에 연결되어 있어. 예를 들어 현재 에셋은:

Soldier Grenade	5	500
Soldier Sniper	10	2,000
Warrior Hammer	5	1,000


즉, 네 프로젝트에서 다음 두 성장은 구별해야 해.
레벨·경험치 성장: 저장되어 다음 플레이에도 이어지는 캐릭터 기록.

조금 더 구체적으로 보면 세 가지가 중요해.
첫째, SaveManager는 파일 담당자 이상의 일을 하고 있어.
파일 읽기·쓰기 외에도 구매, 장착, 슬롯 교환, 보유 기록 보정, 업적 보상, 최고 기록 갱신, 테스트 기능까지 맡아.
이건 클래스를 너무 많이 나눠서 생긴 과설계가 아니라, 한 클래스에 변경 이유가 많이 모인 상태에 가까워.
다만 지금 즉시 여러 인터페이스와 서비스로 분해하는 것부터 시작할 필요는 없어. 먼저 현재 규칙이 어디에 있는지 구분하는 게 우선이야.
둘째, 저장 객체를 외부에서 직접 바꿀 수 있어.
EquipmentModel은 기본 보유 무기를 저장 객체에 직접 추가하고, CharacterProgression은 레벨·경험치를 직접 바꿔.
동작 자체는 성립하지만, 수정과 파일 저장을 짝지어 기억해야 해.
담당자에게 변경을 요청하는 경로와, 기록부에 직접 쓰는 경로가 함께 존재한다.

이것이 현재 구조의 중요한 특징이야.
셋째, 구매·장착 규칙의 검증 위치가 다르다.
EquipmentModel.TryPurchase()는 레벨과 구매 가능 상태를 확인한 뒤 SaveManager에 구매를 요청해.
반면 SaveManager.TryPurchaseWeapon()은 전달받은 ID·가격을 사용하고, 요구 레벨을 직접 조회하지 않아.
장착도 Model은 보유 상태와 중복 장착을 확인하지만, SaveManager의 EquipWeapon()은 같은 검사를 수행하지 않아.
따라서 이렇게 이해하면 돼.
현재 장비 화면의 규칙은 EquipmentModel을 통과할 때 적용된다.
SaveManager를 직접 호출하는 다른 경로에는 같은 검사가 자동으로 따라붙지 않는다.

이것만으로 현재 UI에 구매 버그가 있다고 단정할 수는 없어. 다만 앞으로 다른 화면이나 보상 시스템에서 장비를 지급할 때, 어느 규칙을 거쳐야 하는지를 명확하게 해둘 필요가 있어.
이번 단계 내용을 스스로 확인할 수 있도록 네 프로젝트 기준 답을 남겨둘게.
상황	실제로 확인해야 할 곳
Soldier 기본 HP를 알고 싶다	Soldier CharacterData 에셋
내 Soldier 레벨을 알고 싶다	캐릭터 저장 기록
지금 전투 HP를 알고 싶다	PlayerController
Bullet 기본 공격력을 알고 싶다	Bullet WeaponData 에셋
증강 후 Bullet 공격력을 알고 싶다	해당 슬롯의 WeaponRuntimeState
다음 씬에 어떤 캐릭터를 만들지 알고 싶다	GameSessionManager.SelectedCharacterId
값 변경이 재실행 후에도 남는지 알고 싶다	저장 객체 반영과 SaveToFile() 호출 경로
