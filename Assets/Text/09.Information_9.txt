9-6. 평소 이동과 패턴 이동이 싸우지 않도록 만든다
[BossRandomMover.cs](C:/YSJ/SubPF/Assets/2. Scripts/Enemy/Boss/BossRandomMover.cs)는 보스가 평소 배회하는 움직임을 담당해.

→ 범위 안에서 임의의 목표 위치 선택

목표 위치는 중심에서 x·y 반경을 각각 적용해 고르므로 직사각형 영역 안에서 선택해.
예를 들어 중심이 (5, 0), 반경이 (2, 3)이면:

y: -3 ~ 3
범위 안에서 목표를 고르는 거야.
그런데 돌진 패턴도 Rigidbody를 움직이고, 랜덤 이동도 동시에 Rigidbody를 움직이면 어떻게 될까?
한 사람은 “왼쪽으로 돌진!”이라고 하고,
다른 사람은 “아까 정한 오른쪽 목표로 가!”라고 하는 셈이야.

이를 막기 위해 BossPattern에는 PauseRandomMovement 설정이 있어.
패턴 시작
→ 필요하면 랜덤 이동 정지
→ 패턴이 직접 보스 이동
→ 패턴 종료
→ 랜덤 이동 재개
여기서 [SetControllable(false) (line 249)](C:/YSJ/SubPF/Assets/2. Scripts/Enemy/Boss/BossEnemy.cs:249)라는 이름은 조금 넓게 느껴질 수 있어.
현재 구현에서 직접 막는 것은 공통 랜덤 이동이야. 보스의 피해 처리나 모든 코루틴을 일괄 정지하는 기능은 아니야.
랜덤 이동 재개 시에는 새 목표를 고르지만, 이동 범위의 중심은 최초 초기화 위치를 유지해.
9-7. 일반 패턴은 ‘끝난 뒤 기다렸다가’ 다음 것을 고른다

→ 일반 패턴 B 선택
2초마다 공격을 강제로 시작한다는 뜻이 아니야.

2초: A 시작
6초: A 종료
8초: 다음 일반 패턴 시작
특수 패턴이 진행되는 동안에도 이 타이머는 멈춰.
특수 패턴이 일반 패턴 대기 중간에 시작됐다면, 종료 후에는 남아 있던 대기 시간을 이어서 줄여. 항상 새롭게 2초로 초기화되는 것은 아니야.

9-9. 특수 패턴은 체력 조건마다 한 번씩 요청한다
[Boss_Dog.cs (line 84)](C:/YSJ/SubPF/Assets/2. Scripts/Enemy/Boss/Boss_Dog.cs:84)와 [Boss_Head.cs (line 76)](C:/YSJ/SubPF/Assets/2. Scripts/Enemy/Boss/Boss_Head.cs:76)는 체력 변경 이벤트를 받아 조건을 검사해.

→ 아직 요청하지 않았고 기준 이하라면

→ 특수 패턴 요청

90% 조건 충족 → WideCharge 요청
80% 조건 충족 → SpiralShot 요청
요청 여부는 항목별 bool 배열에 기록해. 체력이 더 줄어도 같은 항목을 다시 요청하지 않아.
또한 이 표시는 실행 완료 기록이 아니라 요청 기록이야.

9-16. 패턴 중단은 ‘코루틴 정지’만으로 끝나지 않는다
[BossPatternRunner.StopAll (line 99)](C:/YSJ/SubPF/Assets/2. Scripts/Enemy/Boss/Patterns/BossPatternRunner.cs:99)은 다음을 처리해.
일반·특수 대기열 비우기
→ 실행 코루틴 정지
→ 보관한 패턴 반복자 Dispose
→ 현재 패턴 참조와 실행 상태 정리
→ 특수 패턴 상태 해제
→ 살아 있다면 필요한 경우 랜덤 이동 재개
반복자를 별도로 보관하는 이유는 패턴에 작성된 finally 정리를 실행하기 위해서야.
예를 들어 경고 완료 이벤트를 구독했다면, 도중에 취소되더라도 구독을 해제할 필요가 있겠지.
하지만 여기서 Runner가 모든 변경을 자동으로 원상 복구한다고 생각하면 안 돼.
- Runner는 자신의 대기열·실행 상태·랜덤 이동 연결을 관리해.
- 외형 회전, 별도 생성물, 패턴이 바꾼 상태는 해당 패턴의 정리 구현이 필요해.
- 이미 생성된 일반 총알을 Runner가 일괄 제거하는 코드는 없어.
실제로 공통 돌진 패턴의 외형 복원은 현재 Execute 끝부분에 있고 finally로 보호되어 있지 않아. 돌진 도중 취소하면 그 끝부분의 복원 코드가 실행되지 않는 구조야. 사망 연출이 기울어진 외형을 이어받을 수 있는 점을 확인할 필요가 있어.
9-17. 객체지향 설계에 대한 판단
이번 구조는 대부분 분리한 목적이 실제 동작과 연결돼 있어.
분리	의미
BossEnemy와 개별 보스	공통 생명주기와 보스별 조건 구분
조건 검사와 Runner	요청 시점과 실행 순서 구분
Runner와 개별 패턴	실행 관리와 공격 구현 구분
Context와 패턴 에셋	현재 보스 참조와 공유 설정 구분
보스 이벤트와 UI·Spawner	주변 시스템이 보스 상태에 반응하도록 연결


따라서 현재 구조 전체를 과한 객체지향이라고 보지는 않아.
다만 정리할 근거가 분명한 부분은 있어.
① Dog와 Head의 체력 조건 검사 코드가 거의 같다
설정 검증, 요청 여부 배열, 이벤트 구독, 체력 조건 검사까지 거의 같은 흐름이야.
일반 패턴은 공통 Controller로 분리했는데, 체력 패턴 조건은 두 클래스에 반복되어 있어.
현재라면 공통 체력 패턴 Controller를 두고 두 보스가 사용하도록 만드는 방향을 검토할 만해. 이미 존재하는 중복을 줄이는 작업이라 목적도 명확해.
그렇게 정리한 뒤 Dog·Head에 고유 코드가 거의 남지 않는다면, 그때는 두 클래스를 계속 구분할 이유도 함께 판단하면 돼.
② 중단 시 복구 책임이 일관적이지 않다
Runner에는 중단 정리 장치가 있지만, 개별 패턴이 모든 임시 변경을 같은 기준으로 정리하지는 않아.
새로운 상속 계층을 더 만들기보다 먼저:
“패턴이 변경한 외형·피해량·생성물·이벤트 구독은 정상 종료와 취소 때 누가 정리하는가?”

이 기준을 통일하는 것이 중요해.
③ 이름과 주석이 실제 책임보다 넓거나 오래된 부분이 있다
- SetControllable: 실제 핵심 제어 대상은 랜덤 이동.
- 시스템 경고 연결 주석: 실제 연결 담당과 차이가 있음.
- BossChargePattern: 정상 종료 시 같은 회전 복원 코드가 두 번 있음.
이런 부분은 작은 문제처럼 보여도, 프로젝트를 설명하거나 유지보수할 때 흐름을 헷갈리게 만들어.
이번 단계에서 연결해야 할 핵심 문장은 이거야.
보스별 조건 검사가 패턴을 요청하고, Runner가 현재 패턴을 마친 뒤 우선순위에 따라 하나씩 실행한다. 패턴은 Context로 실제 보스를 조작하며, 보스의 상태 이벤트를 통해 UI와 일반 적 소환이 함께 반응한다.
