여기서 중요한 차이가 있어.
GameSessionManager는 씬을 넘어 정보를 유지하지만, 그것만으로 파일에 저장되는 것은 아니야.
- GameSessionManager: 지금 실행 중인 게임에서 다음 화면으로 넘길 정보.
- SaveManager: 게임을 껐다 켜도 다시 불러올 정보.
현재 메인 메뉴에서는 GameSessionManager와 AchievementManager가 GameRoot에 있고, SaveManager는 그 아래 자식 오브젝트에 있어. GameSessionManager가 루트를 DontDestroyOnLoad로 유지하기 때문에 자식도 함께 유지되는 구성이야.
싱글턴과 씬 간 유지도 별개 개념이야.
- 싱글턴: 공통 접근 지점과 중복 인스턴스 제어.
- DontDestroyOnLoad: 씬 전환 시 오브젝트 유지.
네 프로젝트에서는 이 둘을 함께 사용하고 있어.

선택한 캐릭터가 누구인지 확인하고, 프리팹을 생성하고, 무기를 지급하고, 적에게 플레이어를 알려줘야 해.
이 작업을 [StageManager.cs (line 104)](C:/YSJ/SubPF/Assets/2. Scripts/Stage/StageManager.cs:104)가 맡고 있어.

```mermaid

    A["StageManager.Start"] --> B["GameSessionManager에서<br/>선택한 캐릭터 ID 확인"]
    B --> C["CharacterDatabase에서<br/>CharacterData 조회"]
    C --> D["캐릭터 프리팹 생성"]
    D --> E["PlayerController 초기화<br/>기본 HP · 이동속도 적용"]
```

이때 핵심은 Initialize야.
예를 들어 적 소환 시스템은 처음부터 이번 플레이어가 누구인지 알 수 없어. 캐릭터를 선택한 다음 생성하기 때문이지.
그래서 StageManager가 다음과 같이 알려주는 거야.
“이번 출격 플레이어는 이 오브젝트야. 앞으로 적을 만들 때 이 플레이어를 공격 대상으로 넘겨줘.”

이런 식으로 외부에서 필요한 참조를 전달하는 것을 의존성 주입이라고 부를 수 있어. 별도의 복잡한 프레임워크가 있어야만 의존성 주입인 것은 아니야.
네 프로젝트에서는 Initialize(...)를 통해 직접 전달하고 있어.

2-8. 기본 무기는 언제 ‘진짜 내 장비’가 될까?

2-10. 그런데 경험치는 전투 중 얻는데 왜 다음 게임에도 남을까?
관련 파일: [CharacterProgression.cs (line 36)](/C:/YSJStudy/SubPF/Assets/2. Scripts/Character/CharacterProgression.cs:36)
“전투 중 바뀌는 값은 전부 사라진다”라고 외우면 여기서 틀려.
어디에서 바뀌었느냐보다 저장 경로로 연결되어 있느냐가 중요해.
CharacterProgression.Initialize()는 저장된 레벨과 경험치를 읽어 자신의 현재 값으로 복사해.
전투 중 경험치를 받으면:
1. 현재 경험치를 증가시킨다.
2. 레벨업 조건을 충족하는 동안 레벨업을 처리한다.
3. 필요한 경험치와 남은 경험치를 다시 계산한다.
4. 저장 객체에 레벨과 경험치를 반영한다.
5. UI에 변경을 알린다.
6. SaveToFile()을 호출한다.
7. 레벨업했다면 업적을 검사한다.
현재 필요 경험치 공식은 다음과 같아.
다음 레벨에 필요한 경험치 = 100 + (현재 레벨 − 1) × 50

예를 들어 레벨 1, 경험치 90에서 경험치 30을 받으면:
- 현재 경험치가 120이 된다.
- 레벨 1의 필요 경험치 100을 소비한다.
- 레벨은 2가 된다.
- 경험치 20이 남는다.
- 레벨 2의 다음 필요 경험치는 150이다.
- 저장 기록에 레벨 2, 경험치 20을 반영하고 파일에 쓴다.
한 번에 많은 경험치를 받아 여러 번 레벨업할 수 있으므로 if가 아니라 while을 사용하고 있어.
그리고 현재 확인한 성장 경로에서는 레벨업이 기본 HP·무기 공격력을 자동으로 올리지는 않아.
레벨은 장비 요구 조건과 업적 판단에 연결되어 있어. 예를 들어 현재 에셋은:
무기	요구 캐릭터 레벨	가격
Soldier Grenade	5	500
Soldier Sniper	10	2,000
Warrior Hammer	5	1,000


즉, 네 프로젝트에서 다음 두 성장은 구별해야 해.
레벨·경험치 성장: 저장되어 다음 플레이에도 이어지는 캐릭터 기록.
전투 증강: 이번 전투의 플레이어·무기 상태를 바꾸는 강화.

경험치는 AddExp() 처리 중 저장되므로, 클리어할 때만 한꺼번에 확정되는 방식은 아니야. 정상적으로 파일 저장까지 끝난 경험치는 이후 전투에서 실패하더라도 이미 기록되어 있어.
2-11. 이번 범위에서 객체지향이 과한 부분은 있을까?
내 판단은 데이터 종류를 분리한 것은 적절하고, 정리할 지점은 데이터 변경 규칙이 여러 곳에 흩어져 있는 부분이야.
구조	판단
CharacterData와 캐릭터 저장 기록 분리	적절함. 공통 설정과 개인 진행도를 구별한다.
WeaponData와 WeaponRuntimeState 분리	적절함. 원본 설정과 개별 전투 상태를 구별한다.
CharacterDatabase, WeaponDatabase	현재 규모에 충분히 단순하다.
세션과 파일 저장 분리	적절함. 화면 이동 정보와 영구 기록의 수명이 다르다.
저장 클래스에 함수가 거의 없음	문제라고 보기 어렵다. 저장할 값을 담는 역할이 분명하다.
기본 장비 처리가 여러 곳에 분산	정리 우선순위가 높다. 같은 빈 슬롯을 다르게 해석한다.
SaveManager의 넓은 역할	책임 집중을 검토할 지점이다.


조금 더 구체적으로 보면 세 가지가 중요해.
첫째, SaveManager는 파일 담당자 이상의 일을 하고 있어.
파일 읽기·쓰기 외에도 구매, 장착, 슬롯 교환, 보유 기록 보정, 업적 보상, 최고 기록 갱신, 테스트 기능까지 맡아.
이건 클래스를 너무 많이 나눠서 생긴 과설계가 아니라, 한 클래스에 변경 이유가 많이 모인 상태에 가까워.
다만 지금 즉시 여러 인터페이스와 서비스로 분해하는 것부터 시작할 필요는 없어. 먼저 현재 규칙이 어디에 있는지 구분하는 게 우선이야.
둘째, 저장 객체를 외부에서 직접 바꿀 수 있어.
EquipmentModel은 기본 보유 무기를 저장 객체에 직접 추가하고, CharacterProgression은 레벨·경험치를 직접 바꿔.
동작 자체는 성립하지만, 수정과 파일 저장을 짝지어 기억해야 해.
담당자에게 변경을 요청하는 경로와, 기록부에 직접 쓰는 경로가 함께 존재한다.

이것이 현재 구조의 중요한 특징이야.
셋째, 구매·장착 규칙의 검증 위치가 다르다.
EquipmentModel.TryPurchase()는 레벨과 구매 가능 상태를 확인한 뒤 SaveManager에 구매를 요청해.
반면 SaveManager.TryPurchaseWeapon()은 전달받은 ID·가격을 사용하고, 요구 레벨을 직접 조회하지 않아.
장착도 Model은 보유 상태와 중복 장착을 확인하지만, SaveManager의 EquipWeapon()은 같은 검사를 수행하지 않아.
따라서 이렇게 이해하면 돼.
현재 장비 화면의 규칙은 EquipmentModel을 통과할 때 적용된다.
SaveManager를 직접 호출하는 다른 경로에는 같은 검사가 자동으로 따라붙지 않는다.

이것만으로 현재 UI에 구매 버그가 있다고 단정할 수는 없어. 다만 앞으로 다른 화면이나 보상 시스템에서 장비를 지급할 때, 어느 규칙을 거쳐야 하는지를 명확하게 해둘 필요가 있어.
이번 단계 내용을 스스로 확인할 수 있도록 네 프로젝트 기준 답을 남겨둘게.
상황	실제로 확인해야 할 곳
Soldier 기본 HP를 알고 싶다	Soldier CharacterData 에셋
내 Soldier 레벨을 알고 싶다	캐릭터 저장 기록
지금 전투 HP를 알고 싶다	PlayerController
Bullet 기본 공격력을 알고 싶다	Bullet WeaponData 에셋
증강 후 Bullet 공격력을 알고 싶다	해당 슬롯의 WeaponRuntimeState
다음 씬에 어떤 캐릭터를 만들지 알고 싶다	GameSessionManager.SelectedCharacterId
값 변경이 재실행 후에도 남는지 알고 싶다	저장 객체 반영과 SaveToFile() 호출 경로
